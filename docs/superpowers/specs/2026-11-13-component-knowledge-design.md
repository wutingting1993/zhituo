# 页面组件知识查询设计

状态：用户已于 2026-11-13 批准核心设计。最新指示：先接入当前服务，沿用当前技术栈；本文原独立服务部署边界由该指示覆盖。

## 目标

开发者在系统页面开启开发者模式并选中组件后，以系统编号、项目号、前端页面路径、组件 ID 和接口列表查询相关知识，结合新需求交给模型。第一阶段服务于开发者自己的本地工作区。

长期目标是支持需求澄清、方案确定、开发与部署。当前设计只覆盖知识查询和上下文交付，不实现后续执行编排。

## 已确认边界

- 采用独立知识条目＋适用关系，知识正文保持唯一。
- 组件业务知识包括组件自身、所在页面和业务流程中适用于它的规则。
- 查询服务返回关联规则及适用条件，由模型判断是否适用于当前需求，不建设规则执行引擎。
- 前端自动分析组件动作和接口关系，暂不存储该关系。
- 前后端代码地址关联系统、项目和接口服务，不直接关联组件。
- 不存储类、方法等模型可自行查找的代码定位信息。
- 不考虑知识录入方式、代码版本匹配。
- 不引入登录权限、日志监控等附加功能。

## 方案比较与选择

1. 按组件保存完整知识：查询简单，但页面、流程及接口的共享规则重复。
2. 按流程、页面、组件层级汇总：层级直观，但跨层复用及条件适用表达受限。
3. 独立知识条目＋适用关系：正文唯一，可复用并保留适用范围；需要维护关联。

用户选择第三种。不限定数据库产品，不要求图数据库。

## 概念模型

| 对象 | 内容及关系 |
| --- | --- |
| 系统、项目 | 系统编号、项目号；关联前端本地代码地址和后端服务 |
| 后端服务 | 在系统、项目范围内唯一的服务标识；关联后端本地代码地址 |
| 页面 | 系统、项目范围内的页面路径；关联业务流程 |
| 组件 | 系统编号＋项目号＋页面路径＋组件 ID 联合唯一 |
| 业务流程 | 流程标识及说明；页面可以关联多个流程 |
| 接口 | 系统、项目、服务标识、HTTP 方法、实际接口路径联合定位 |
| 知识条目 | 稳定编号、类别、正文、来源、确认状态；可表达业务规则、术语、接口说明与技术口径 |
| 适用关系 | 知识条目与流程、页面、组件或接口的关联；包含适用条件和已明确的例外、替代关系 |

服务标识的命名范围、页面多流程、接口定位字段以及下面的查询细节是设计者建议，随本文确认，不作为用户已确认的独立事实。

适用条件先以自然语言表达，不设计条件语言或自动计算。无条件适用必须明确标记，不能把条件缺失自动解释为无条件。知识状态区分已确认、待确认、已失效；失效知识不进入默认正文，仅在存在显式引用时提示。来源描述知识依据，不自动等同于已确认。

本地地址通过开发者当前工作区的映射解析，不把某台机器的地址当成全体开发者共享事实。多开发者配置及录入机制不在本次范围。

## 查询输入与解析

必需输入：系统编号、项目号、页面路径、组件 ID。接口列表允许为空；每项含 HTTP 方法与接口地址。

所有接口统一采用 /{服务标识}/{实际接口路径}。例如 /swe/api/xxx 解析出 swe 和 /api/xxx；swe 用于获取后端代码地址，服务标识、方法和实际路径用于查询接口知识。

查询参数不参与接口身份匹配；路径中的业务参数需要对应登记的接口模板。实现者可选择路径模板匹配方式，但不能在多条匹配时任意选取。接口列表无法定位时返回明确缺口，不让模型猜测接口身份。

新需求和页面业务上下文由调用方随模型任务传递，不作为组件唯一标识，也不是知识查询的必需输入。模型缺少判断条件时应提出澄清。

## 查询流程

1. 根据四项联合标识定位组件及所属页面，获取页面关联的流程。
2. 获取组件、页面、流程直接关联的知识；保留每条适用关系及条件，不自动把流程全部规则认定为适用。
3. 逐项解析接口列表，查找服务代码地址与接口知识；不推断组件动作和接口的绑定。
4. 汇总去重知识正文，保留全部关联来源与条件，不因去重丢失适用范围。
5. 返回结果、未匹配项和已知冲突。部分缺失不阻止其余结果返回；区分对象不存在、对象存在但未关联知识、服务未映射、接口未匹配及匹配歧义。

仅沿上述显式关系查询，不自动扩展到全部上下游或全部引用方。影响分析、代码内部依赖、未登记调用由模型结合代码后续分析。

## 返回给模型的上下文

- 查询对象：系统、项目、页面、组件及入参接口。
- 业务知识：唯一知识正文，附类别、来源、确认状态及所有适用关系、条件。
- 接口知识：解析后的接口身份、相关业务说明及技术口径；技术口径可包含实际存在的过滤、去重、精度、事务、幂等及异常约定，不强制每个接口填写全部类别。
- 代码地址：前端工作区地址、按服务归组的后端工作区地址；缺失时明确报告。
- 缺失与冲突：未匹配对象、未登记知识、缺少定位字段、已知冲突及例外、替代依据。

不承诺自动发现所有语义冲突。服务返回已登记冲突和原始依据，模型可进一步识别并提出问题。不得按组件优先、最新记录优先等隐含规则裁决。

## 模型使用约定

模型结合新需求、查询结果及本地代码判断知识适用性；待确认内容不能视为已确认事实，条件未知或规则冲突应进入需求澄清。查询成功不等于知识充分，也不授权修改代码或部署。

后续全流程应另行设计任务状态、确认节点、验证和部署约定及知识回写，本次不预先实现这些能力。

## 验收场景

以下是设计验收依据，不授权新增或运行测试：

- 同一组件可以取得自身、页面及流程的关联知识，并保留各自条件。
- 同一规则被多个对象引用时只返回一份正文，引用关系完整。
- /swe/api/xxx 能取得 swe 对应代码地址及正确方法下 /api/xxx 的接口知识。
- 接口列表为空仍能查询组件业务知识。
- 一个接口未匹配时，其余组件及接口知识仍可返回。
- 条件未知、规则待确认或存在冲突时，结果明确表达，不静默裁决。
- 返回内容不包含预存的组件到类、方法绑定，不依赖代码版本信息。

## 留给实现者的选择

数据库、接口传输形式、字段命名、索引和地址映射配置方式由后续方案决定，沿用实施项目实际技术栈。正式接口契约在实施前单独确定并同步接口文档。本设计不要求当前仓库安装依赖、修改业务代码或提交 Git。
