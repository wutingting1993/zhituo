# 项目知识文档组织与维护设计（报表项目首个应用）

状态：待用户批准。本文批准前不迁移现有文档，不实现维护工具。

## 目标与边界

建立可用于不同业务项目的知识组织与维护方法，为开发提供可定位的当前规则、模块差异、契约与验证证据。报表是首次应用，不是通用模型的前提。会话期间自动积累任务知识，用户主动指定一组相关任务归档时才合并长期知识；存量口径变更受确认控制。

用户已选择“公共规则＋报表专项＋变更记录”。纯新增且不影响既有规则时自动维护；存量口径或规则变更须确认，尤其是全局影响。本文将用户的“存新增”理解为“纯新增”，该解释随本文一并确认。

不修改业务代码、数据库、接口或现有业务口径；不新增运行平台、依赖、CI、测试或监控。不追溯补造历史确认和验证事实，不自动提交 Git。

## 方案比较

- 按报表保存完整知识：单报表阅读方便，但公共规则重复，变更容易遗漏。
- 单份集中大文档：入口统一，但体积持续增长，模块差异难管理。
- 公共规则、报表专项与变更记录分开：通过稳定编号建立引用，需要维护链接，但可明确权威来源和影响范围。用户已采纳此方案。

## 通用知识模型

采用“项目共享知识＋模块专项＋变更记录”，不要求项目必须有报表、指标、数据库或 HTTP 接口。

| 知识类别 | 职责 | 适用示例 |
| --- | --- | --- |
| 入口与范围 | 导航、模块清单、状态及权威来源 | 项目、子系统、业务域 |
| 共享规则与术语 | 多模块共同遵守的业务含义、约束及边界 | 订单状态、金额精度、报表日期 |
| 数据与外部契约 | 数据来源、结构及模块间或对外约定 | 表关系、文件格式、事件、API |
| 模块专项 | 本模块目标、行为、引用规则与专有约定 | 报表、审批、批处理、客户端功能 |
| 决策与变更 | 原因、差异、影响、批准及替代关系 | 全局规则调整、技术方案选择 |
| 实现与验证证据 | 规则如何落地及实际验证范围 | 代码位置、人工核对、已授权检查结果 |

上述类别是职责划分，不是每个项目必须创建的目录。没有相关内容时不创建空文件；小项目可合并文件，但保留职责和权威边界。指标是报表的数据定义专项，其他项目不强制建立指标目录。

建议以 docs/knowledge/README.md 为通用入口，按需使用 shared/、modules/、contracts/、changes/；现有项目已有合理目录时优先复用，通过入口和链接组织，不要求物理迁移。共享规则必须声明作用域：项目级、业务域级或模块级；“多个模块引用”不自动意味着全项目适用。引用范围扩展按存量变更处理。

唯一权威、稳定标识、确认/实现/验证分离、影响分析及新增/变更审批边界对所有项目适用。文件名、编号前缀和细分目录由项目决定，不建立通用运行框架。当前先在本仓库写明规则，制作可安装的跨项目技能或规范模板属于后续独立范围。

## 本项目文档映射

沿用仓库 Markdown 与相对链接，不引入独立知识系统。本项目以 docs/knowledge/README.md 为总入口，链接报表领域入口 docs/reports/README.md。以下是报表领域的具体映射建议，尚未创建，并非其他项目必须复制的目录。

| 路径（相对于 docs/reports/） | 职责 |
| --- | --- |
| README.md | 知识入口、报表清单、状态、推荐阅读顺序及待确认事项链接 |
| common/rules.md | 公共筛选、日期、机构、去重、空值、基准与展示精度规则 |
| common/data-lineage.md | 表字段、关联链路、记录保留和过滤规则；区分业务含义与技术映射 |
| common/metrics.md | 公共指标定义、公式、分子分母、去重键、适用范围与边界 |
| modules/summary.md | 顶部统计的用途、范围、公共规则引用及专有行为 |
| modules/plan-coverage.md | 规划覆盖、下钻及三类来源等模块专有规则 |
| modules/execution.md | 执行视角、下钻及新增指标，保留尚未实现状态 |
| api.md | 当前已实现接口契约；拟议接口保留在模块文档，不混入当前接口 |
| changes/README.md | 待确认、已批准、已应用、已撤销变更的索引 |
| changes/YYYY-MM-DD-topic.md | 一次存量规则变更的差异、依据、影响、批准及应用记录 |

已有设计、实施计划和验证记录保留原路径，作为历史依据与证据。迁移完成后，旧需求和接口文档保留简短迁移说明及新链接，删除已迁移的重复现行定义，避免双份维护；历史内容仍可由版本历史追溯。迁移须先核实仓库版本管理条件，无法可靠保留历史时保留原文并明确“历史、非现行依据”。

## 唯一权威与引用

公共规则只在 common 中定义；模块引用规则编号，并明确自己的适用范围、附加限制。模块不得静默覆盖公共定义。公共指标引用数据链路，接口引用模块或指标，验证记录引用对应规则或模块。

编号保持稳定，例如 RULE-DATE-001、METRIC-CONTACT-RATE、MODULE-PLAN-COVERAGE；本轮不建立逐字段大型登记表。规则记录含编号、定义、适用范围、来源依据及相关引用；指标额外记录公式、去重粒度、空值及舍入。修改编号或删除定义按存量变更处理。

文档类型各有职责，不采用“代码永远优先”或“最新文件优先”：已确认规则描述业务意图；当前接口描述对外契约；代码描述实现事实；验证记录描述特定版本和环境的证据。发现不一致时登记待确认问题，不自动把任何一方改成另一方。

## 会话维护与批量归档

自动维护分为任务记录和正式长期知识，只有用户主动归档才触发后者更新。

### 会话期间

新会话及恢复时，读取知识入口、当前任务记录和相关未归档任务摘要；按需读取相关内容，不全量加载。用户的新需求、明确确认、实施进展及验证结果自动记录在任务文件中，附来源和状态，不直接改写正式长期知识。临时假设仍是草案。

已确认的新决定在当前任务中有效；其他相关任务读取时需检查其作用范围，不能默认适用于所有任务。与正式知识不一致的未归档决定必须显式提示，不能静默采用旧定义或把新定义自动推广。

任务完成时形成待归档知识清单，保存未决项与证据；完成不等于归档。不建立定时或后台归档。中断、交接及可预见的上下文压缩前保存最小检查点。

任务记录建议按需置于 docs/knowledge/tasks/，独立文件包含稳定标识、目标范围、来源、关联规则、确认决定、实际改动、验证证据、未决项和下一步。短小任务可复用已有设计或变更文件，不复制正式规则全文，不存储密钥或无关聊天。

### 用户指定一组任务归档

用户可通过任务标识、标题或文件路径指定一组相关任务；归档范围以用户明确指定为准，不自动纳入其他相关任务。若指定对象无法唯一定位，先澄清，不猜测。跨会话内容以可访问的任务记录或获授权读取的会话为依据；证据不可取得时明确缺口。

归档流程：

1. 读取指定任务及其关联正式知识，确认各任务实际完成情况与知识清单。
2. 按规则标识与业务含义合并重复内容，保留所有相关来源；不能只按同名或时间顺序合并。
3. 检查组内冲突、与正式知识的冲突，以及未归档关联任务可能受到的影响。明确批准的替代关系优先；无法确定时生成差异提案，不按最新日期自动裁决。
4. 纯新增且明确无冲突的内容自动写入长期知识；存量变更只应用已明确批准且与当前提案一致的内容。未批准变更单独请求确认，全局变更附引用方和影响范围。
5. 先落地无冲突且不依赖未决变更的部分；未决及依赖部分保留待归档，不将整组标为已归档。
6. 更新长期知识入口、引用、状态及归档记录。归档记录列出任务清单、目标规则、处理结果、批准依据和未决项。各任务分别标注已归档、部分归档或待归档。

再次归档同一任务时只处理新增加或尚未归档的知识，避免重复正文；归档记录保留来源与替代关系。不删除任务证据，不自动关闭或归档 Codex 聊天，不自动提交 Git。

用户提出批量归档即授权执行无冲突新增合并，不视为对未展示的存量语义变更的笼统批准。已批准的同一范围不重复询问。确认、实现、验证分别记录，任务完成或归档都不能自动升级验证状态。

### 接入与执行边界

实施时把会话记录、任务完成清单和批量归档流程接入项目实际生效的代理指引，通过入口链接记录；仅创建目录不能保证自动维护。适用于不同代理工具，不安装全局技能、hook或后台服务。多个会话修改同一知识时应用前重读正式定义，发现变化重新核对，不覆盖其他会话的新内容。工具不可用或内容未落盘时明确未保存范围。

正式 API 说明等现有开发交付文件仍按原任务授权维护；本节控制的是归档形成的长期知识库，不阻止必要的代码和接口交付。归档时核对这些实现资料与规则的差异，不把实现资料自动当成业务批准。

## 当前状态与证据

分别记录业务确认、实现与验证状态，不能以单个“完成”代替三者：

- 业务：待确认、已确认；已被替代的规则链接替代项。
- 实现：未实现、部分实现、已实现；附相关代码或接口位置及可取得的版本依据。
- 验证：未验证、部分验证、已验证；链接日期、环境、范围和结果。历史验证不能证明后续变更已通过。

状态按模块维护，部分完成时列出具体子项。来源包括现有需求、明确确认记录、代码位置及验证文档；找不到来源写“待核实”，不补造批准人、提交号或已验证结论。

初始梳理重点：旧设计 GET 与当前 POST 的差异作为历史演进处理；规划覆盖来源限制仅属该模块；执行视角保留拟议接口状态；技能分类名称暂为 null、最大流失环节取最小值等显式约定不能自动纠正。

## 知识分类边界

纯新增必须语义完整且不改变既有定义；同名不同公式、修改数据范围或扩大适用范围均需检查存量影响。存量变更提案列明旧值、新值、依据、影响规则、模块、契约及验证范围。全局变更检查引用方，未知影响明确列出。无法判断的内容保留待确认。新增证据不自动代表验证通过，测试仍按项目授权执行。

## 通用验收与本项目首次整理

通用验收：每项知识能定位权威来源和作用域；共享与专项无未说明冲突；已确认、已实现、已验证分别有依据；纯新增在主动归档时自动合并，存量语义变更先形成可审阅差异；历史材料明确标识且能追溯。不同项目按实际知识类别验收，不要求报表指标或数据库存在。

### 本项目首次整理与验收

先建立入口与公共规则，再迁移顶部、规划覆盖和执行专项，最后整理接口引用与历史标识。只做有来源的等义抽取；遇到冲突先登记，不在整理中裁决业务。

验收要求：

- 每类现行公共规则有唯一正文；三个模块能定位其公共依赖和专有规则。
- 当前接口与拟议接口分开，历史 GET 设计不再被指为当前契约。
- 每个模块分别给出确认、实现、验证状态及证据，不能将执行需求自动标为已实现。
- 能通过规则编号和文档引用检索受影响模块；新增知识、存量变更、冲突及指定任务组归档各有明确处理路径。
- 本轮无业务语义变化，迁移覆盖项可与原文逐项对照；无法确定的内容列入待确认。
- 文档交付检查内容一致性、相对链接和引用目标；不启动服务、不运行单元或 e2e 测试。

## 留给实施者的选择

实施者可决定同一文件内的标题顺序、等义抽取的批次及链接锚点。不得自行决定业务冲突、扩大迁移范围、增加自动化基础设施或把历史验证升级为当前验证。首次整理无须为每条旧规则追补变更文件，记录原文来源即可。
