# 组件知识整理技能与 MCP 契约重整设计

状态：待用户复核。本文只规定设计，不改变组件知识接口或已发布知识。

## 1. 目标与边界

用户在 Codex 会话中明确提出整理某组件知识后，模型应结合前端 meta、当前前后端代码、会话说明及 MCP 返回的存量知识，盘点该组件适用的全部知识类型，生成可逐条审核的候选草稿并返回现有组件详情页的审核地址。首次无实质存量时做全量候选；有存量时逐类核对，只提交实质增量。技能不发布版本，不自动改业务代码，不遍历无关项目，也不把模型推断当作已确认业务口径。

本次设计文档放在业务项目；拟实施的技能与 MCP 适配器仍属于 Codex 全局安装包。后端已有 `/api/v1/knowledge/maintenance/baseline`，当前主要缺口是全局 MCP 没有暴露首次草稿能力，以及技能缺少连续的生成规则。若实施中发现既有后端契约无法支持本方案，应先报告冲突并调整设计，不自行扩展接口。

## 2. 资料来源和权威边界

1. 用前端生成的 `components.registry.json` 定位组件及 `metaPath`，读取对应 `component.meta.ts`。注册表由 `generate-registry.mjs` 汇总 meta 并生成协作关系；`generate-component-meta.mjs` 只生成骨架，业务语义字段可能由人工填写。读取现有文件，不重新运行生成脚本，也不把生成标记当作业务确认。
2. 从 meta 提取 `id`、`source`、`parent`、`children`、`styles`、`summary`、`accepts`、`presents`、`behaviors`、`stateFlows`、`apiDependencies`。用实际组件及相关状态代码核对行为和展示；冲突列出两边依据。源码位置与装配关系是定位线索，不直接写入业务知识正文。
3. 按 `apiDependencies` 的 `apiId` 到前端端点定义解析方法和地址，保留 `direct` 与 `upstream` 的区别；按现有知识查询配置转换为服务标识地址。`apiDependencies` 未登记不代表明确无接口依赖，需查实际调用并报告无法覆盖的接口。系统、项目、登记页面路径和服务标识来自当前运行配置或用户明确提供的身份，不能以源码路径代替 `pagePath`。缺少关键身份时先澄清，不猜测配置。
4. 带明确身份及已核实的接口列表调用 MCP。已发布对象使用当前清单和明确版本全文；无正式版本时读取 `legacyContext` 与 `sourceRevision`。搜索摘要只用于定位，不能替代完整对象版本。MCP 读取失败不视作“没有存量”。
5. 会话中用户明确说明为 REQUIREMENT；代码直接可观察的行为为 FACT；从实现提炼的业务含义及指标口径为 INFERENCE。代码事实证明当前实现，不自动证明它是已获业务确认的永久规则。

meta 只供取证与形成候选，不作为 MCP 读取或首次基线请求的 `meta` 参数。现有后端会把请求中的 `meta` 注入原始快照，并在基线组装时将组件对象标为 CONFIRMED；不传它可以避免把尚待审核的描述提前写入已确认基线。meta 衍生的组件说明通过独立候选在详情页审核。

## 3. 首次与增量判定

在 MCP 成功读取后，判断后端**原有**实质知识：已发布清单的完整对象，或旧上下文中已有说明、业务/技术规则、接口契约、适用关系、页面流程、交互与组件联动。仅有组件和页面身份骨架、空名称/说明，不算存量。判断时不计本次会话提供的 meta、代码归纳或未发布候选。

| 存量判定 | 当前正式版本 | 盘点和提交 |
| --- | --- | --- |
| 无实质知识 | 无 | 全量盘点；有可提交候选时走首次基线草稿 |
| 无实质知识 | 有 | 全量盘点；相对当前清单走普通草稿 |
| 有实质知识 | 无 | 相对旧上下文做增量；因无正式版本，仍走首次基线草稿 |
| 有实质知识 | 有 | 相对当前明确版本做增量；走普通草稿 |

全量/增量决定候选覆盖范围，有无版本决定草稿提交路径。每次仍检查该组件适用的全部类型；首次有证据的完整知识成为候选，增量只提交实质差异。缺失证据不是“明确无内容”，不构造空对象凑数；无实质变化时不为记录活动创建草稿。

## 4. 一条连续的整理流程

技能入口按如下顺序组织，不要求模型跨数份规则文档自行拼流程：

1. 定位组件并读取 meta、必要的前端代码和接口身份，随后读取 MCP 存量及明确版本。
2. 按第 3 节判断首次或增量；建立逐类盘点表。每条记录包括对象类型、稳定 ID/版本（如有）、存量内容、meta 线索、前后端代码位置、会话依据、结论、候选动作和缺口。结论限定为新增、实质修改、关联调整、冲突、无变化、证据不足、不适用。“不适用”也须有依据。
3. 对当前组件的展示项、筛选和状态追踪到前端计算、实际调用，再追踪明确关联的后端路由、业务处理和查询。提炼过滤、分组、分子分母、公式、时间边界、异常与缺省处理；由代码推导的业务规则/指标口径可作为 INFERENCE、PENDING 候选。只看到展示值而未看到计算来源时只记已核实部分，不补造公式。
4. 按第 5 节逐类判断，匹配稳定 ID 后生成 CREATE/UPDATE/LINK/UNLINK/UPGRADE_REFERENCE/EXPIRE 等独立 Change；实质差异才提交。完整候选 content、基准版本、证据、确认状态和依赖原子组必须可追溯至盘点记录。
5. 校验身份、引用、字段树、必填/可空、条件、来源及完整性；按版本状态选择提交工具。首版提交使用读取时的 `sourceRevision` 及**原样相同且顺序一致**的接口列表，读和提交均不注入 meta。基准或快照变化时停止旧草稿提交，重新读取与对照；不得静默重试失效候选。
6. 只返回服务实际给出的审核链接、逐类盘点结论、候选摘要、冲突和未覆盖范围；用户在现有详情页选择并确认发布。技能和 MCP 不暴露发布能力。

## 5. 九类对象的生成与约束

| 对象 | 盘点与生成内容 | 判断边界 |
| --- | --- | --- |
| COMPONENT | 名称、用途、接受输入、呈现内容、行为、状态流转 | 从 meta 提取并核对组件代码；只保留知识正文需要的说明，不写源码路径/装配元数据；已存在身份骨架用 UPDATE，不重复 CREATE |
| PAGE / FLOW | 当前页面和明确登记流程的名称、用途 | 页面身份不能凭源码路径猜测；流程仅有显式登记或用户明确说明才生成 |
| KNOWLEDGE | 业务规则、指标口径、技术规则；确需持久记录时的口径冲突 | 代码可推导候选规则和公式，但推断标 INFERENCE、PENDING；业务目标与现状冲突时不擅自裁决，也不把完整接口字段重复为规则 |
| INTERFACE | 用途、方法/地址、请求与响应媒体类型、逐层出入参字段说明、错误、示例、规则引用 | 核对实际前后端契约；每个已核实字段说明含义、类型、必填/可空及有依据的校验；证据不足不制造字段 ID、公式、说明或示例 |
| APPLICABILITY | 规则适用目标、条件、例外、明确替代关系 | 未知条件不等于无条件；共享规则只处理当前组件明确引用，不替其他组件升级 |
| PAGE_FLOW | 页面到流程的显式关系 | 不按组件装配、目录层级推断 |
| INTERACTION | 当前组件的动作、触发条件、提供内容、自身响应 | meta 协作信息可帮助定位，但需核对实际交互；response 不是 HTTP 响应 |
| COMPONENT_RELATION | 交互作用于目标组件的影响和条件 | 仅明确关联；同用接口或共享规则不自动推出直接或传递联动 |

匹配不确定或证据相互冲突时列待确认；模型推断不标 CONFIRMED。未提及、未读到或未观察到的旧知识不删除。UNLINK 只解除当前组件引用；EXPIRE 需明确的全局停用依据。新增规则及其关联必须以同一原子组保证审核选择完整。首次基线可能已有组件/页面骨架：候选需匹配原有稳定 ID 并 UPDATE，不能按“没有实质知识”错误地 CREATE 重复身份对象。

## 6. 技能与接口契约组织

`SKILL.md` 是顺序执行的主手册，包含触发边界、六步流程、逐类盘点格式、差异到 Change 的映射、提交门槛、首次与增量各一个端到端示例。精确调用结构不散落在主手册。每个 MCP 工具在 `references/contracts/` 下独立一份可直接使用的契约文件：

| MCP 工具 / 契约文件 | 后端对应操作 | 契约重点 |
| --- | --- | --- |
| `read_component_knowledge` / `read-component-knowledge.md` | `/context` | 身份、接口列表、当前/历史对象、旧上下文、`sourceRevision`、空存量判定 |
| `search_knowledge_objects` / `search-knowledge-objects.md` | `/objects/search` | 搜索范围、分页、摘要不等于全文 |
| `read_knowledge_object_version` / `read-knowledge-object-version.md` | `/objects/version` | 对象身份与明确版本、完整正文、不可隐式回退 |
| `list_knowledge_object_versions` / `list-knowledge-object-versions.md` | `/objects/history` | 历史版本与分页，不把列表当正文 |
| `submit_knowledge_draft` / `submit-knowledge-draft.md` | `/drafts/create` | 已有正式版本时的变更、幂等键、完整 Change 与审核地址 |
| `submit_initial_knowledge_draft` / `submit-initial-knowledge-draft.md` | `/baseline` | 无正式版本时提交身份、`requestId`、`sourceRevision`、与读取时相同的 `interfaces` 及 `changes`；无 `meta` 注入 |
| `read_knowledge_draft` / `read-knowledge-draft.md` | `/drafts/read` | 草稿修订、预览、问题与审核地址，不允许发布 |

每份契约写明工具名、用途、完整入参及可空/必填、模型实际收到的返回数据形状（与后端 HTTP Result 信封区分）、嵌套字段、错误/冲突处理、调用示例和不变量。提交类文件须自含完整 Change 与对象 content 的适用字段说明；INTERFACE 类型须覆盖出入参逐字段的 `meaning`、`detail`、`validation`、`required`、`nullable` 及字段稳定 ID。主手册在使用步骤处链接对应文件；旧的多端点总契约不再作为模型的操作入口，避免互相矛盾的重复指令。不另增业务接口文档产物。

## 7. 失败边界与验收

- MCP 读取失败、身份不唯一或对象明确版本无法完整读取：停止相应判断；不把缺口当作无知识。其他独立且可核实的条目可单独整理。
- meta、代码、用户要求或存量互相矛盾：展示双方证据；可提交待确认推断，但不自动裁决为 CONFIRMED。
- 接口字段的说明缺证据：保留已有合法值，明确列出接口、方向和字段路径的缺口；不能把缺省误作“无需说明”。
- 首次快照 `sourceRevision` 变化、正式基准变化或草稿被页面编辑：停止沿用旧候选，重新读取和对照，不覆盖用户修订。
- 草稿仅由工具创建，不发布；审核 URL 必须来自服务响应。没有可审核的实质变化时说明无变更，不制造版本。

实施验收检查两个场景：身份骨架且无实质存量时全量候选可走首次草稿；有存量时逐类盘点、仅提交变更。另检查旧知识无正式版本、正式版本空清单、接口列表一致性、代码推断 PENDING、字段说明缺口和基准冲突。验收时先验证技能结构、每份契约引用、MCP 工具声明及适用的编译/静态检查；未经单独授权不运行单元或 E2E 测试，也不向真实组件提交验证草稿。
