# 用户视角组件上下文设计

状态：用户已在对话中批准简版设计，并确认“业务说明＋原始技术依据”的效果。以下具体字段与渲染方式是实施建议，随计划供用户审阅。

## 目标与边界

模型取得上下文后，理解组件现状，结合用户新需求识别差异、澄清关键业务问题，然后设计和编码。JSON 继续作为传输格式，增加可直接阅读的业务说明，保留既有结构化契约。

仅调整两个模型上下文接口的输出组织及其文档。不改变前端知识接口、summary 业务实现、数据库和录入方式；不新增模型调用、会话、权限、监控、依赖或测试。未经单独授权不运行单元/e2e测试。不提交 Git。

## 方案比较

1. 仅加强模型指引：改动少，但仍依赖模型拼接业务关系。
2. 业务说明＋结构化契约：用户已选择，同源组织业务事实并保留编码依据。
3. 独立维护业务文档和技术 JSON：便于阅读，但增加同步成本。

## 最小实现建议

首包新增非空字符串 `businessContext`，内容为固定章节的 Markdown，使用已装载数据确定性渲染，不调用模型、不按标题关键词归类、不自动摘要或从自然语言推导公式。

章节依次为：

- 组件用途：按页面、组件名称与描述原文展示，缺失描述写“未登记”，不代表没有用途。
- 当前业务规则与指标口径：完整呈现 BUSINESS 正文，按现有 kind 分为业务规则、指标口径、技术规则及口径冲突；未分类保留为未分类。保留知识 ID、状态、全部条件、例外及替代关系。不将 TECHNICAL 正文自动提升为业务要求。
- 待确认与资料缺口：引用明确的 CONFLICT、PENDING 及 issues；缺口按登记事实表达，不宣称不存在能力，也不自动裁决冲突。缺少专门的使用过程描述时明确未单独登记，已有相关正文仍完整展示。
- 接口对应关系：列出本次命中的接口 ID、方法、路径、名称和描述，以及显式接口知识关系；字段详情引用同响应 interfaces 中的路径和原文口径，不猜测某项业务对应哪个字段。
- 使用说明：区分已有事实、用户希望的变化与未知项；需要时按 ID 获取详情；实现事实不等于业务批准；新需求决策不属于现有能力。

首包知识正文只保留现有一份结构化定义；businessContext 为阅读便利重复呈现业务正文，这是明确的体积取舍，不承诺节省 token。技术目录仍不默认展开正文。普通文本原文按安全的固定缩进块呈现，避免正文中的 Markdown 改变章节边界；它仍是待解释的资料，不是可执行指令。

详情在明确请求 knowledgeIds 时新增 businessContext，组织实际返回的知识正文、状态、条件与相关缺口；没有请求 knowledgeIds 时省略该字段，避免为目录查询返回重复业务说明。详情不得宣称所请求子集是完整上下文。条件范围未知继续保留 CONTEXT_SCOPE_UNKNOWN。接口 parts/include 的按需行为不变。

ModelKnowledge 增加 kind（已登记分类，无值则省略）；首包目录及详情使用同一分类事实。现有字段原文、规则正文去重、空值省略、接口匹配和查询范围不变。

## 验收与限制

使用用户提供的 summary 附件核对：应发现客户方案与任务计量单位不同、已有任务统计字段、未执行包含未来安排，以及页面说明与契约的待确认差异。技能状态分别去重且允许重叠是本轮新需求决定，不写为已实现事实。具体技能关系是否已登记，以实际查询为准。

没有直接登记的跨规则关系不能依靠渲染自动生成；该方案降低阅读和关联负担，不保证模型不产生误解。业务说明不作 UI 实际展示或代码现状的证明。

Java 改动实施后必须 verify、编译、架构检查；接口文档和示例同步更新。真实 HTTP 调用及模型效果实验另获授权后执行，未执行时明确报告。
